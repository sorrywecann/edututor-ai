# v0.6.3 — Fixes from v0.6.2 Live Dev-Machine Session

**Date:** 2026-05-30 04:30 CEDT
**Trigger:** Live test of v0.6.2 surfaced 3 distinct bugs

## Bug A — UE5 never reconnects after backend bounce

### Symptom (observed live)
1. v0.6.2 booted cleanly: backend healthy, UE5 connected, `clients=1`, avatar broadcasts visible
2. I killed backend (testing whisper cache fix)
3. Orchestrator auto-respawned backend (`restart 1/5`)
4. UE5 process stayed running BUT WebSocket connection was dead
5. `/avatar/status` returned `{"connected":false,"clients":0}` permanently
6. No `ue5-monitor` log lines anywhere → monitor never even started

### Root cause (two compounding bugs)

**A1. `_restartDependent` short-circuits on `noRestart`.** `orchestrator.mjs:458`:
```js
if (!spec || spec.noRestart || !rec || !rec.proc) return;
```
UE5 spec has `noRestart: true` (because the inner cooked game is self-stable on its own crashes). But `noRestart` was overloaded — it both blocked auto-restart on UE5's own crash AND blocked dependent-driven restarts triggered by backend bounce.

When backend's `_onExit` fires `_restartDependent('ue5')`, this returns immediately. UE5 never gets killed/respawned.

**A2. Mid-session monitor (`_startUE5MidSessionMonitor`) never started.** v0.6.2 launcher.log showed the boot sequence reaching `ue5 spawn` and stopping — no `launcher ready` line. Most likely cause: `_startService(ue5)` got wedged inside `waitForAvatarConnection` or the self-heal block, so the `for (const spec of this.specs) await this._startService(spec);` loop never completed → `emit('ready')` never fired → `_startUE5MidSessionMonitor()` never ran.

### Fix

**A1 fix** (`orchestrator.mjs` `_restartDependent`):
- Drop `spec.noRestart` from the short-circuit. `noRestart` retains its meaning for the `_onExit` path (UE5 crashing on its own) but no longer blocks dependent bounces.
- Also `taskkill /IM SlovakEdu.exe /T /F` on Windows so the inner game proc dies (cooked builds have stub + inner game; stub is what we track).

**A2 fix** (`orchestrator.mjs` `start()` + monitor):
- Per-spec try/catch in the boot loop, so a hung/throwing spec cannot prevent `emit('ready')` or monitor start.
- Log `<spec> startService completed` after each spec — visible boot progress.
- Log monitor start banner.
- Monitor logs every 60s (`pollCount % 12 === 1`) so we can see it polling even when there's nothing to do.
- **Consecutive-zero gate** — require 2 zero readings (~10s) before respawning UE5. Avoids false trigger during the brief mid-handshake window after backend respawn.
- **Fresh-spawn fallback** — if proc tracker has lost the UE5 reference entirely (`!rec || !rec.proc`), monitor now spawns UE5 itself instead of returning silently.

## Bug B — STT crashes on first mic click ("hf_xet missing")

### Symptom (observed live)
```
RuntimeError: faster-whisper init failed: To use optimized download using Xet storage,
you need to install the hf_xet package. Try `pip install "huggingface_hub[hf_xet]"`
or `pip install hf_xet`.
```
Triggered by `GET /api/v1/stt/models` on first hit. Backend stays alive but voice input is broken until backend is killed + cache populated by hand.

### Root cause
`huggingface_hub` 1.17.0 (bundled) defaults to **Xet storage** for HF Hub downloads. The required `hf_xet` Python package (Rust-backed wheel) is NOT in the bundle, so `xet_get(...)` raises `ValueError`.

Our v0.6.0 pre-baked the MiniLM RAG model in the bundle's HF cache. But `Systran/faster-whisper-small` was NOT pre-baked — backend was trying to download it on first use, hitting the Xet path.

### Fix (`stage-resources.mjs`)
Refactor the single-model staging into an `HF_MODELS` array:
```js
const HF_MODELS = [
  { id: 'sentence-transformers--paraphrase-multilingual-MiniLM-L12-v2', label: 'RAG embedding (MiniLM)',  approxMb: 458 },
  { id: 'Systran--faster-whisper-small',                                label: 'STT (faster-whisper-small)', approxMb: 244 },
];
```
Each model is copied from host `~/.cache/huggingface/hub/` into `resources/backend/hf-cache/hub/`. On first launch, `ensureHfCacheExtracted` copies the whole hub into `<userData>/hf-cache/` (writable). Backend's `HF_HOME = <userData>/hf-cache` finds both snapshots locally — zero Xet, zero network.

**Cost:** installer grows ~250 MB (886 MB → ~1.14 GB).
**Benefit:** STT works offline-first-launch; eliminates Xet dependency entirely.

### Why not just ship `hf_xet`?
Tradeoff considered. Cons:
- Still requires HF network on first STT call (slow first ~30-60s of voice activation).
- `hf_xet` is a platform-specific Rust wheel — extra fragility for Windows-only bundle.
- Pre-baking is the same pattern we already use for MiniLM. Consistency wins.
